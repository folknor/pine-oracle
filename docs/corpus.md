# The corpus

## What it is

PineForge ships a public corpus repository at <https://github.com/fullpass-4pass/pineforge-corpus> containing 235 Pine v6 reference strategies, each cross-validated trade-for-trade against TradingView's broker emulator. Total: ~313,000 trades verified. Apache-2.0 licensed. (PineForge's engine repository at <https://github.com/fullpass-4pass/pineforge-engine> consumes the corpus as a git submodule.)

It is the only published large-scale TradingView parity test suite. For piners, where matching TV trade lists is the killer differentiator, the corpus is the executable specification.

## What is in each probe folder

`corpus/validation/<NN-slug>/` contains four files:

- `strategy.pine`: the canonical Pine v6 source for the probe.
- `generated.cpp`: PineForge's transpiler output (closed-source transpiler, but the *output* is shipped). Compiles against `libpineforge.a` to produce a strategy `.so` that exports the 10-symbol C ABI. **piners ignores this file**: we are not consuming PineForge's engine.
- `tv_trades.csv`: TradingView's trade list, exported from TV's "List of Trades" pane after running `strategy.pine` against the canonical OHLCV feed on the TV chart. This is the ground truth.
- `engine_trades.csv`: PineForge's trade list, regenerated by their CI after running their compiled `.so` against the same OHLCV. Useful as a reference second opinion (PineForge hits 227/228 excellent), but not strictly required.

Plus an optional `inputs.json` for per-probe configuration: `runtime_overrides` (bar magnifier mode, OHLCV trim), `ohlcv_start_ms` (warmup trim), `expected_tier` (anomaly/engine_only overrides), `validation_overrides.expect_tv_match`. Most probes do not have one.

## The OHLCV feed

`corpus/data/ETHUSDT_15.csv` (or similar; PineForge has shipped a few revisions). 36k-bar Binance ETH/USDT:USDT 15m feed; the benchmark variant in `benchmarks/assets/data/ETHUSDT_15.csv` is the extended 53,930-bar variant covering 2024-10-20 to 2026-05-04 (about six months pre-TV-export warmup + the full TV chart range). Public market data, committed for reproducibility.

Same feed, every probe. Comparing strategies across probes is therefore apples-to-apples; comparing piners-vs-PineForge-vs-TV on the same probe is bar-aligned.

## How PineForge uses it

`scripts/run_corpus.sh` builds each probe's `generated.cpp` into a strategy `.so`, runs each `.so` against the feed via `scripts/run_strategy.py` (ctypes harness), emits `engine_trades.csv`, then `scripts/verify_corpus.py` diffs each `engine_trades.csv` against its `tv_trades.csv` and prints a tiered summary. Headline result: 227/228 excellent, 1 documented anomaly.

The verifier:

1. Aligns trades by direction + entry-time within a 1-hour gating window with a 3 dollar entry-price gate.
2. Trims both lists to the matched-trade window plus or minus 1h (eliminates edge-trade count inflation when engine and TV disagree on warmup boundary).
3. Honors `inputs.json` per-probe.
4. Computes 4-dimension p90 deltas vs TV: trade count, entry price, exit price, P&L.
5. Classifies into 5 tiers: excellent -> strong -> moderate -> weak -> minimal. Strategies with `trail_*` exits get a relaxed exit + PnL threshold profile.

## How piners uses it

piners does not need PineForge's C++ harness. CSVs are language-agnostic. The harness shape we need:

1. Load `corpus/validation/<probe>/strategy.pine`.
2. Either (a) compile via piners' Pine -> bytecode pipeline (when we have one), or (b) load a hand-translated Rust strategy (during bootstrap).
3. Run the piners engine against `corpus/data/ETHUSDT_15.csv`.
4. Emit `piners_trades.csv` in TV schema.
5. Diff against `tv_trades.csv` using a clean-room Rust port of `verify_corpus.py`'s alignment + tier logic.
6. Pass/fail per the canonical thresholds.

Everything but step 2 is mechanical and writable in a day. Step 2 is the actual piners project.

## Why it matters

1. **Pre-paid forensic work.** Each probe was designed to exercise a tricky v6 semantic (intra-bar path resolution, fill priority, magnifier, intraday cap, deferred flip, pyramiding, OCA, partial exits, etc.) and the TV ground truth was exported case by case. Recreating this from black-box TV would cost the same effort PineForge already spent.

2. **Language-agnostic test oracle.** Trade lists are timestamps, prices, sides, sizes, PnL. No PineForge code is needed to use them. Rust diffs CSVs as well as C++ does.

3. **CI-shaped on commit one.** Each probe is a self-contained pass/fail unit. Once the harness is in place, piners has 228 parity tests immediately. Regressions surface trivially: any probe that drops a tier in a commit is a bug.

4. **Public Apache-2.0.** No license friction. Credit PineForge in NOTICE; vendor the `corpus/` directory either as our own git submodule pointing at PineForge's repo, or as a vendored copy in `piners/corpus/` (more brittle but offline-friendly, and decouples us from PineForge's tagging cadence).

## Bootstrap strategy: hand-translation before transpiler

The chicken-and-egg problem: to validate the engine against the corpus, you need to *run* `.pine` source; to run `.pine` source, you need a Pine -> bytecode transpiler; to know the transpiler is correct, you want to validate it against the corpus.

Resolution: invert the order. Before piners has a working transpiler, manually translate the first 50 probes' `strategy.pine` to handwritten Rust strategies against a `trait Strategy` interface. Run those against the OHLCV feed via the engine. Diff against `tv_trades.csv`. Iterate the engine until all 50 are excellent.

The hand-translations are then the **test corpus for the transpiler**: when the transpiler comes online, it must produce Rust strategies that match the hand-translated ones (functionally, not byte-for-byte). Two independent paths converging on the same trade list. The transpiler ships when it can match the human translation on a probe it has never seen before.

This bootstrap also forces the engine to be designed for hand-authored Rust strategies, not only for transpiler-generated ones. PineForge's engine is officially "internal C++ headers, not for external consumption"; piners' engine should be a peer-friendly Rust trait, with the transpiler being one of multiple consumers.

## The 1 documented outlier

`anomaly-equity-mirror-strategy-equity-01`. PineForge's engine produces a different trade list than TV at the 1x equity boundary because TV's broker emulator is non-deterministic on that probe (rounding behavior on a margin edge case differs between TV runs of the same source on the same OHLCV). PineForge calls itself correct; TV is the noise. The probe is tagged `expected_tier = "anomaly"` in `inputs.json` so the verifier does not count it as a regression.

piners should inherit the same treatment: anomaly tier, not a parity failure.

## Vendoring plan

Two reasonable options:

**A. Git submodule pointing at PineForge's `corpus/`.** Tracks their updates automatically; one `git submodule update --init corpus` brings in everything. Downside: piners is yoked to PineForge's submodule cadence and any rebases on their side.

**B. Vendored copy in `piners/corpus/`.** One-time `git subtree add` (or just `cp -r`), committed to piners. Downside: drifts from upstream over time; we choose when to resync.

Recommend **A** for the indicator/strategy CSVs (228 probes, ~5 MB of CSVs + .pine), **A** for the OHLCV feed too (it is a known-good Binance snapshot that PineForge will rev when they extend the chart range). If we ever need a piners-specific subset (skip probes that exercise features piners does not yet support), gate that in the harness via an allowlist file, not by mutating the corpus.

## Open questions

1. **License acknowledgment.** Apache-2.0 requires `NOTICE` attribution. Confirm the wording when piners' license is chosen.
2. **OHLCV provenance.** PineForge pulls from Binance public API. If piners' production data layer uses a different provider for ETHUSDT 15m, parity will break for reasons unrelated to the engine. The corpus harness should always use the corpus's bundled OHLCV, not piners' default data source.
3. **TV export cadence.** PineForge's `tv_trades.csv` files were exported from TV at specific times. If TV changes broker semantics in a Pine version update, the ground truth ages. Track PineForge's corpus revisions; their CI is the canary.
4. **Probe selection for the bootstrap.** First 50 probes is arbitrary. Better criteria: cover one probe per `strategy(...)` feature flag, one per fill-priority edge case, one per exit type. Map probe slugs to features and pick a covering set.
